Missing Scenarios

Gateway-to-bank settlement delay is not modelled. Successful payment immediately debits ESC-001 escrow bank in ledger-event-handlers.js (line 70), but in real PG flow funds often sit as gateway receivable until gateway settles to nodal/escrow.
Partial capture, partial refund, multiple refunds, refund after settlement, and refund failure/reversal are missing as first-class flows.
Chargeback lifecycle is thin: chargeback received, evidence submitted, provisional debit, merchant won/lost, representment, arbitration fees, and recovery from future settlements are not fully modelled.
Settlement batching is missing. Payment success creates one settlement per transaction in ledger-event-handlers.js (line 190), while real settlements are merchant/date/bank-account/cycle batches.
Bank payout outcomes are incomplete: bank accepted, bank rejected, UTR duplicate, beneficiary name mismatch, IFSC invalid after validation, transfer reversed, return after success, NEFT delayed, and IMPS timeout are not represented.
Reconciliation lacks fee/GST/TDS/withholding/tax rounding scenarios. Matching compares mostly orderId and amount in reconciliation-service.js (line 81).
Bank escrow reconciliation is balance-level only in reconciliation-service.js (line 290). It does not match bank statement lines by UTR, narration, value date, debit/credit, opening/closing balance, or running balance.
External duplicate transactions are not properly detected. externalMap overwrites duplicate orderIds instead of flagging them.
Multi-currency is nominally allowed in payment validation, but ledger/accounting/reporting assumes INR in many places.
Webhook replay, out-of-order events, late success after failure, duplicate callback, and manual status correction flows are not production-grade.
Identified Gaps

Ledger failure is allowed after payment success. payment-gateway.js (line 345) and QR flows log ledger errors but do not fail or queue compensation. This can create successful transactions with no ledger entry.
Settlement creation failure is also swallowed in ledger-event-handlers.js (line 211), creating payment-ledger-settlement divergence.
Settlement status schema evolved to CREATED/FUNDS_RESERVED/..., but some reports still query pending/processing in compliance-reports-service.js (line 145). Merchant outstanding reports will be wrong.
Revenue report filters for ledger event types platform_fee and gateway_fee, but payment revenue is posted under payment_success, so platform revenue can be understated in compliance-reports-service.js (line 249).
Settlement state transitions do not invoke bank APIs, reserve actual ledger balance, lock funds, or post settlement ledger entries. The state machine is operational, not financially final.
utr_number is indexed but not unique in 20240104000000_ledger_system.js (line 198), so duplicate payout confirmations can slip through.
transaction_ref, idempotency_key, settlement_ref, and payment_orders.order_id are globally unique, not tenant-scoped. This can cause cross-tenant collisions.
merchants has no tenant_id, while reports join tenant settlements to global merchants. That weakens tenant isolation.

Risk Areas

Financial misstatement: recognizing escrow cash at payment success can overstate bank balance before gateway settlement.
Duplicate payout risk: no unique UTR constraint, no bank idempotency key, no payout instruction table, and retries can resend without proving prior bank outcome.
Merchant overpayment risk: refunds/chargebacks after settlement are not netted against future settlements or recovered through merchant reserve.
Reconciliation blind spots: balance-level escrow reconciliation can pass despite wrong individual transactions.
Audit risk: swallowed ledger/settlement failures create breaks that are only discoverable later.
Operational risk: no outbox/DLQ means failed ledger posting, merchant webhook, settlement creation, and bank callbacks can be lost.
Compliance risk: reports are not reproducible if cached mutable JSON is used without source snapshot/versioning.
Scale risk: reconciliation loads full period transactions into memory and uses JS maps; this will strain for large daily volumes.

New User Stories

As a finance operator, I want gateway settlements reconciled by settlement report line, so that fees, taxes, net amount, and delayed settlements are visible.
Acceptance criteria: matches by gateway payment id and settlement id; detects fee/tax/net mismatches; detects duplicate external rows; creates unresolved recon items for every mismatch.

As a settlement system, I want to batch merchant settlements by cycle and eligibility, so that one bank payout represents many transactions.
Acceptance criteria: excludes unsettled refunds/chargebacks/holds; stores included transaction ids; computes gross, fees, adjustments, reserves, net; prevents the same transaction appearing in two active batches.

As a bank operations user, I want payout status to handle returned/reversed transfers, so that merchant balances are corrected after a bank return.
Acceptance criteria: supports BANK_RETURNED after BANK_CONFIRMED; reverses settlement ledger entries; reopens payable or moves amount to suspense; logs bank return reason.

As a reconciliation analyst, I want bank escrow reconciliation at statement-line level, so that balance matches do not hide wrong postings.
Acceptance criteria: imports opening/closing balance; matches by UTR/narration/date/amount; flags unmatched bank debits/credits; supports suspense and approved adjustment.

As a risk analyst, I want refunds and chargebacks after settlement recovered from future payouts, so that merchants are not overpaid.
Acceptance criteria: creates merchant recoverable; deducts from next settlement; blocks settlement if recoverable exceeds payable unless credit policy allows negative carry-forward.

As a platform, I want durable ledger posting via outbox, so that successful payments cannot silently miss ledger entries.
Acceptance criteria: every successful transaction creates an outbox event; failed ledger posting retries with backoff; unresolved failures appear in ops queue; payment and ledger reconciliation flags missing ledger entries.

As a compliance auditor, I want immutable report snapshots tied to source ledger ranges, so that RBI reports are reproducible.
Acceptance criteria: report stores source period, ledger transaction range/hash, generated_by, generated_at; final reports cannot be overwritten; regenerated draft shows variance.

As a treasury user, I want settlement fund reservation to lock available merchant payable, so that concurrent settlements cannot reserve the same funds.
Acceptance criteria: reservation is atomic; concurrent requests cannot double-reserve; reservation expiry/release is supported; reservation appears in ledger or reservation table with audit trail.

High-Level Architecture

Use an event-driven, ledger-first architecture where operational systems can fail and retry, but financial intent is never lost.

Core principle: payments, settlements, refunds, chargebacks, and reconciliation should not directly mutate financial state in scattered services. They should emit durable financial events, which are processed into immutable ledger entries, settlement records, payout instructions, and reconciliation exceptions.

The target architecture should have these layers:

Payment Processing Layer

Handles authorization, capture, webhook intake, payment status transitions.
Does not directly assume money reached escrow.
Emits events such as PAYMENT_AUTHORIZED, PAYMENT_CAPTURED, PAYMENT_FAILED, GATEWAY_SETTLEMENT_RECEIVED.
Financial Ledger Layer

Owns all accounting postings.
Maintains immutable double-entry ledger.
Models gateway receivable, escrow bank, merchant payable, platform revenue, reserves, recoverables, refunds, and chargebacks.
All financial state is derived from ledger plus controlled operational state.
Settlement Layer

Builds merchant settlement batches.
Applies eligibility rules, holds, refunds, chargebacks, reserves, and deductions.
Reserves payable atomically before bank payout.
Creates payout instructions but does not mark settlement final until bank confirmation.
Bank Transfer Layer

Owns payout instruction lifecycle.
Handles bank idempotency, bank request IDs, UTRs, status callbacks, rejects, returns, reversals, and timeout recovery.
Reconciliation Layer

Reconciles gateway settlement files/API reports.
Reconciles bank escrow statements at transaction-line level.
Produces discrepancy items and suspense/adjustment workflows.
Risk and Dispute Layer

Owns refund and chargeback lifecycle.
Creates merchant recoverables where settlement has already happened.
Feeds settlement deductions.
Control and Compliance Layer

Auth/RBAC, maker-checker approvals, audit logs, immutable reports, period close, ledger locks.
Finance operations cannot rely on spoofable headers.
Event Reliability Layer

Outbox, workers, retry queues, dead-letter queues, operational alerts.
Ensures no successful payment silently misses ledger or settlement processing.

Critical Design Decisions

Do not debit escrow bank at payment success

Payment capture should create gateway receivable and merchant payable/conditional payable.
Escrow bank is debited only when gateway settlement to nodal/escrow is confirmed.
Ledger posting must be durable

Payment success may return to customer only after transaction state and outbox event are durably committed.
Ledger worker can retry, but missing ledger entries must become visible operational exceptions.
Settlement is batch-based

One settlement per payment is not production-valid.
Settlement batches must aggregate eligible items by merchant, cycle, currency, and bank account.
Bank payout finality requires bank confirmation

SENT_TO_BANK is not settlement.
BANK_CONFIRMED needs bank reference/UTR.
BANK_RETURNED must reverse or reopen merchant payable.
Reservation prevents double payout

Funds must be atomically reserved before payout instruction.
Settlement item uniqueness prevents the same ledger transaction from being settled twice.
Reconciliation must be line-level

Balance-level reconciliation is only a summary control.
Real reconciliation requires transaction-line matching and exception workflow.
Tenant isolation must be enforced at the database level

Business references should be unique per tenant, not globally.
Merchant records must carry tenant_id.
Critical finance APIs require real RBAC and maker-checker

Header-based role checks are not acceptable.
Sensitive actions require authenticated user identity, role, approval policy, and audit trail.
Refunds and chargebacks are settlement-affecting financial events

If before settlement, reduce payable.
If after settlement, create merchant recoverable and deduct from future settlements.
Reports must derive from financial truth

Merchant outstanding should come from merchant payable/recoverable ledger balances.
Settlement aging should use settlement batch states.
Platform revenue should come from revenue ledger accounts, not event type filters alone.

Sprint 1.5
You are a senior backend engineer working on a financial system.

We have already implemented:
- Durable outbox_events table
- Outbox worker with retry + DLQ
- Idempotency enforcement
- Basic RBAC

Now we must HARDEN the system.

--------------------------------------------------
GOAL
--------------------------------------------------

1. Make outbox the ONLY source of truth for all financial side effects
2. Ensure the outbox worker is safe under concurrency, crashes, and retries

This is critical for financial correctness.

--------------------------------------------------
PRIORITY 1 — REMOVE DIRECT LEDGER WRITES
--------------------------------------------------

Requirements:

1. Remove any direct ledger writes from request/transaction flow.
   - No ledger posting inside payment-gateway or API handlers.
   - No fallback "try ledger then outbox".

2. All financial side effects MUST happen via outbox events only.

3. Ensure:
   - Transaction write + outbox event are committed atomically
   - Ledger posting happens ONLY in outbox worker

4. Update existing code paths:
   - payment-gateway
   - any ledger-service direct invocation

5. Ensure backward compatibility:
   - No duplicate ledger entries
   - No missing ledger entries

--------------------------------------------------
PRIORITY 2 — HARDEN OUTBOX WORKER
--------------------------------------------------

Implement the following:

### 1. Row-level locking (CRITICAL)

Use:

SELECT ... FOR UPDATE SKIP LOCKED

Requirements:
- Only one worker processes a given event
- Support multiple concurrent workers safely
- Prevent duplicate processing

---

### 2. Processing timeout recovery

Problem:
Events stuck in PROCESSING if worker crashes

Solution:

Add:
- processing_started_at
- processing_timeout_seconds (configurable)

Worker logic:
- If status = PROCESSING AND timeout exceeded:
    → reset to PENDING
    → increment retry_count

---

### 3. Idempotent handler execution

Requirement:
Event handler must be safe to run multiple times

Implement:
- Check idempotency_key before applying side effects
- Ensure ledger posting is idempotent
- Prevent duplicate financial impact

---

### 4. Safe state transitions

Enforce strict transitions:

PENDING → PROCESSING → PROCESSED
PENDING → PROCESSING → FAILED → (retry)
FAILED → DLQ

Prevent:
- skipping states
- double processing

---

### 5. Retry + DLQ correctness

Ensure:
- retry_count increments correctly
- next_retry_at respected
- max_retries moves event to DLQ
- dlq_at timestamp recorded

---

### 6. Logging & traceability

Every event processing must log:
- event_id
- correlation_id
- idempotency_key
- retry_count
- final status

--------------------------------------------------
TESTING REQUIREMENTS
--------------------------------------------------

1. Update existing tests where behavior has changed:
   - Remove assumptions of direct ledger writes
   - Ensure tests expect outbox-driven execution

2. Add integration tests for:

- Concurrent workers:
  → same event processed only once

- Worker crash simulation:
  → event recovers from PROCESSING to PENDING

- Idempotent execution:
  → same event processed twice → no duplicate ledger entry

- Retry behavior:
  → failure → retry → success

- DLQ flow:
  → failure after max retries → DLQ

3. Tests must use REAL database (no mocks)

4. Use --runInBand compatible design

CONSTRAINTS

- Do NOT bypass outbox
- Do NOT introduce race conditions
- Preserve tenant isolation
- Preserve idempotency guarantees

--------------------------------------------------
OUTPUT EXPECTATIONS
--------------------------------------------------

- Updated implementation (worker + services)
- Removed direct ledger writes
- Hardened worker logic
- Updated + new integration tests
- All tests passing
